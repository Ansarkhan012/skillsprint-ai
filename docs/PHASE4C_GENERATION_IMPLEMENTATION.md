## Stage decision

The original SRS requires staged onboarding and gives example time horizons, but does not mandate exact day windows. Phase 0 describes configurable stages; Phase 3 stores immutable stage revisions and approved RRM stage references. `GENAI_CONTRACT.md` requires a pinned stage set. The only provided live fact is that `public.onboarding_stage_definitions` currently has zero rows. Therefore the five stages below are the explicitly requested **application-owned competition default**, not facts extracted from a company policy:

| Order | Code | Label | Start day | End day |
| --- | --- | --- | ---: | ---: |
| 0 | ORIENTATION | Orientation | 0 | 1 |
| 1 | POLICIES_COMPLIANCE | Policies & Compliance | 1 | 3 |
| 2 | ROLE_TRAINING | Role-Specific Training | 2 | 5 |
| 3 | PRACTICAL_APPLICATION | Practical Application | 4 | 7 |
| 4 | ASSESSMENT_COMPLETION | Assessment & Completion | 7 | 7 |

These windows organize plan presentation only. They never supply a policy trigger/deadline. For example, approved text “Within 7 days” remains AMBIGUOUS without an approved trigger, and Phase 4A preflight blocks generation. An Admin may later create a new immutable stage revision/set; historical sets and generated snapshots remain pinned.

It is transactional and creates no stage rows at migration time: `created_by` requires a real ACTIVE profile. The project owner applied it once to the existing Phase 3 database. Do not reapply it automatically. The first Admin then calls `POST /api/v1/onboarding-stage-sets/bootstrap` with the normal authenticated bearer session. The RPC derives `created_by` from `auth.uid()` via `current_profile_id()`, checks ADMIN, serializes bootstrap/activation with a transaction advisory lock, inserts the five revision-1 stage definitions and `STANDARD_EMPLOYEE_ONBOARDING` version 1, audits the operation, and returns the set ID. A second exact call returns the same set. Partial or conflicting configuration fails closed; it is not overwritten. Bootstrap uses no service-role credential. `onboarding_stage_sets` has a partial unique index permitting at most one ACTIVE set. Set items cannot be updated/deleted; activation deactivates the prior set and activates the new one atomically. No ACTIVE set blocks generation. The pinned input snapshot contains exact set/version/stage-revision IDs; RRM stage assignments must belong to that set. Future configuration is a separate Admin-only create/activate RPC, not mutation of historical membership.

## Persistence and authorization

`generation_runs` stores a frozen Phase 4A input, canonical hash, matrix and stage-set pins, prompt/template/schema versions, provider configuration without a key, caller identity, and lifecycle state. States are `QUEUED → RUNNING → UNVERIFIED | FAILED | STALE_INPUT`; there is no VERIFIED state or approval/edit/delete API. `generation_attempts` and `generated_plans` are append-only/immutable. A plan row can exist only as UNVERIFIED. Audit events cover stage configuration, request/start, each attempt, and terminal outcome; audit metadata contains hashes/codes, not credentials or full generated content.

`POST /api/v1/generation-runs` requires Admin or Training Manager, `employee_id`, and an `Idempotency-Key`. The server derives all ground truth using the caller JWT/RLS, performs deterministic Phase 4A preflight, reserves the input through a guarded RPC, claims the run under a row lock, invokes the Phase 4B provider, records bounded attempt metadata, rechecks preflight, and requests a guarded terminal transition. SQL also checks approved matrix/current ground truth, employee and stage configuration, canonical hashes, and source/requirement identity before reservation. A postflight change results in STALE_INPUT, with no published plan. A provider failure produces FAILED. Idempotency uses a unique `(actor,employee,key hash)` constraint and checks input/prompt/schema versions; a second unique active-input index prevents concurrent duplicate provider execution for the same actor/employee/input/prompt/schema. A replay of a claimed or completed run never calls the provider. Another distinct key for an already active input is rejected by the DB unique index.

`GET /api/v1/generation-runs` is paginated and `GET /api/v1/generation-runs/{run_id}` returns safe provenance, attempts and, if available, structured UNVERIFIED output. Admin and Reviewer may read all; Training Manager reads their own runs; Manager, Employee and anon cannot access them. Reviewer cannot create. Stage-set reads are Admin/Training Manager/Reviewer. Authenticated users have SELECT only where RLS allows; they have **no direct table write grants**. Public/anon have no grants. The narrow public-schema RPCs have authenticated-only EXECUTE, fixed `search_path=''`, actor checks from the JWT, and protected transitions. The private helper schema has no caller access. The scoped live authorization results below support these boundaries; actual-row cross-user visibility and lifecycle transitions were not tested live.

Direct authenticated RPC invocation remains possible for an authorized Admin/Training Manager. The RPC validates frozen authoritative input and state, but PostgreSQL cannot attest that a remote Gemini call actually occurred or perform the full Pydantic output validation. Consequently Phase 4C content is explicitly UNVERIFIED; deterministic Phase 5 validation and human review remain mandatory. It must never be treated as approved ground truth.

## Phase 4D bounded provider projection (review candidate)

The full immutable `generation-context/1.0.0` snapshot and its `input_hash` remain the authoritative persisted input. The new `generation-projection/1.0.0` deterministically selects required employee attributes, every applicable requirement with exact timing and source identifiers, every dependency, and every fixed stage. It excludes raw source content, evidence excerpts, profile/audit fields, and duplicate matrix metadata. The provider receives this projection rather than the entire frozen snapshot; the full snapshot remains available to deterministic parsing and postflight checks. No requirement, dependency, timing rule, source reference, or stage is truncated to fit the bound.

The new `phase4d-bounded-generation/1.0.0` prompt contract pins a separate SHA-256 `projection_hash` alongside the historical full `input_hash`, template hash, provider and model. A deterministic 24,576-byte projection bound returns `GENERATION_PROJECTION_TOO_LARGE` after safe reservation/claim but before any provider call; the run is finalized as FAILED with no partial plan. The additive `supabase/migrations/202609250003_bounded_generation_projection.sql` creates a separately named reservation RPC and nullable projection-hash column. Historical rows and the old RPC/prompt contract are left unchanged. This migration is **not applied** and requires independent manual review/application before the new backend generation path can be used. No provider run or Phase 5 validation is claimed by this implementation.
